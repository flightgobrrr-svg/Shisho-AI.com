### The drafting agent now has a free live path (Gemini) — confirmed working end-to-end

- `app/api/assistant/route.ts` calls **Gemini (`gemini-3.6-flash`, Google AI Studio's free tier)** if `GEMINI_API_KEY` is set, falling back to the pre-existing Claude path if only `ANTHROPIC_API_KEY` is set, falling back to demo mode if neither is. Gemini wins when both are present. This was the user's explicit ask this session: a live agent "for free as of rn" rather than waiting on a paid Anthropic key.
- **Model choice was live-tested, not assumed:** `gemini-3.7-flash` (the newest Flash model, and what a first pass at this picked) returned 503 "high demand" on every attempt against the real API. `gemini-2.5-flash` 404s outright — Google's own error body says it's retired for new API keys and points at 3.6. `gemini-3.6-flash` is what actually completed a real drafting request. **Re-check both of those before assuming this is still current** — 3.7 being overloaded is plausibly temporary, and Google could retire 3.6 the same way it did 2.5.
- **A real, confirmed API-vs-docs mismatch:** Google's own structured-output docs describe `"type": ["string", "null"]` (JSON-Schema-style nullable) as valid for `responseSchema`. The live API rejects it — `400 INVALID_ARGUMENT`, *"Proto field is not repeating, cannot start list."* Gemini's schema is proto-backed: a single `type` string plus a separate `nullable: true` boolean is what it actually accepts, and `additionalProperties` isn't a recognized field either. This is why `GEMINI_RESPONSE_SCHEMA` in the route is a hand-kept second copy of `ASSISTANT_SCHEMA` rather than the same object reused — the two providers' schema dialects are incompatible, not just differently formatted. **Don't trust Gemini's own docs at face value for schema syntax again without testing against the live endpoint** — this cost a real debugging cycle this session.
- Same system prompt (`DRAFTING_SYSTEM_PROMPT`), same context-prefix convention (workspace doc type, draft excerpt, the default-template instruction) — factored into shared `withContextPrefix`/`toAssistantResponse` helpers in the route file so the two providers can't quietly drift apart on what the model is told or how its output is parsed.
- Calls Gemini's REST `generateContent` endpoint directly via `fetch` (not a new SDK dependency): `systemInstruction.parts[].text`, `contents[].{role: "user"|"model", parts[]}`, `generationConfig.{responseMimeType: "application/json", responseSchema}`, auth via `x-goog-api-key` header. Google's newer "Interactions API" (GA since June 2026) is now the promoted default in their own docs, but `generateContent` is confirmed still fully supported with no announced sunset — chosen here because the Interactions API's own docs don't yet clearly show system-instruction or multi-turn history support, which this agent needs.
- File attachments (PDF/image native, .docx/.txt extracted via the same `mammoth` call as before) now convert to either provider's shape via `lib/assistantFiles.ts`'s `fileToContentBlock` (Anthropic) or new `fileToGeminiPart` (Gemini) — both now share one `extractTextIfNeeded` helper so the .docx/.txt decode logic exists exactly once.

### Every judgment now has a live, on-demand "citation digest" page — real judgment text in, a full law-report-style analysis out

The Legal Library's search results now link to `app/library/judgments/[slug]` — a full digest (headnote, synopsis, ratio decidendi, judicial analysis, practical litigation application, and a dozen more sections) in a format the user specified exactly, built to look like a professionally published SCC/AIR citation digest: court name bold at top, side headings only, no numbering, no decorative text.

**This went through two real architecture changes before landing, both worth understanding if this gets touched again:**

1. **First version (abandoned): AI-drafted from the model's own memory of the case**, no source text at all — same shape as the drafting agent's existing trust model. Worked, but was a materially weaker trust boundary than everything else this Library holds itself to, and the user asked for something better.
2. **Second version (current): the real judgment's own text, fetched live.** `lib/indianKanoon.ts` fetches the case's already-verified `sourceUrl` (a specific, known document — never a search, which is the fragile/ToS-risky way to use Kanoon) and parses out court, title, raw citations, and bench from Kanoon's own consistently-labelled markup (`h3.docsource_main`, `h2.doc_title`, `h3.doc_citations`, `h3.doc_bench`) — confirmed accurate against real pages, not guessed. Everything else — case number, date, nature of proceedings, and the entire 18-field analytical digest — is derived by the model (`lib/caseBrief.ts`) strictly from that real fetched text, with an explicit instruction never to draw on its own memory of the case and never to copy verbatim from any existing headnote or digest (the user's own style requirement, and also the right call legally — SCC/AIR's own headnotes are separately copyrighted in India). **Verified accurate against real, well-documented facts for multiple landmark cases** (Kesavananda Bharati's 13-judge/7:6 basic-structure holding, Maneka Gandhi's "golden triangle" of Articles 14/19/21 with a real citation to R.C. Cooper, Kihoto Hollohan's Paragraph-7-severed/Speaker-as-Tribunal holding) — not just plausible-sounding, actually checked against known real holdings.
- A judgment longer than ~300,000 characters (Kesavananda Bharati chief among them — one of the longest judgments in Indian legal history) gets the middle truncated, keeping the opening and closing portions, where the facts and the actual holding live.
- **No pre-seeding, no batch verification pass — explicitly rejected by the user.** An earlier session-internal attempt to batch-generate all 84 cases ahead of time was abandoned deliberately: Indian Kanoon is already the verified source, so there is nothing left to independently verify before a request; the system should just answer live when someone actually asks. `getCaseDigest` still checks a Supabase cache first and writes to it after generating (so a second visitor to the same case is instant) — that part was kept as a transparent performance detail, not something the user needs to think about, since nothing about "answer live" implies "make the second visitor wait through the same multi-minute generation the first one did." Revisit this specific call if that reasoning turns out to be wrong.
- **A real, live-confirmed constraint that shaped the final model choice:** `gemini-3.6-flash`'s free tier turned out to be a hard 20 requests/DAY on this project — confirmed via an actual 429 mid-testing, not documented anywhere in advance (Google doesn't publish per-model free-tier numbers, only shows them in your own AI Studio dashboard). This affects the EXISTING live draft-bot too, not just this feature — both `app/api/assistant/route.ts` and `lib/caseBrief.ts` were switched to `gemini-3.6-flash`'s sibling, `gemini-3.5-flash`, a separate quota bucket, confirmed working. **Check current availability AND quota for whichever model is live before assuming it's still right** — this is now the second time this exact lesson has cost real debugging time this session.
- A full digest generation genuinely takes real time on a cache miss — anywhere from under a minute (most cases) to several minutes (the handful of outlier-length judgments), since it's a single ~16,000-token structured generation over the judgment's full real text, not a quick lookup. `app/library/judgments/[slug]/loading.tsx` covers this with an honest "this can take a few minutes the first time, instant after" message — a ROUTE-SCOPED loading file, deliberately not using the root-level `app/loading.tsx` (which is still disabled — see below), since this specific page is already dynamic and doesn't hit the bug that root file has with static routes.

The table's shape changed twice this session as the feature itself changed; both times the fix was `drop table` + recreate, explicitly called out in the file as safe specifically because this table holds nothing but a regeneratable cache.

## 5. Hard-won gotchas — read before debugging

- **Next.js 16 renamed `middleware.ts` → `proxy.ts`** (function name too). Check `node_modules/next/dist/docs/` before writing gate/redirect code.
- **Reading `headers()`/`cookies()` in the ROOT layout forces the entire site off static generation.** Use a client-side `usePathname()` check instead (`ChromeGate.tsx`, `HtmlLangSync.tsx`).
- **This repo's files are CRLF.** A naive `\n`-split script silently does nothing meaningful.
- **Only one `next dev` process per project directory.** If one's already up, `preview_start({url:"http://localhost:3000"})` instead of `{name:...}`.
- **The Browser pane's own console-message buffer accumulates across the whole tab's lifetime and does not clear on navigation** — a "fresh" error you just saw might be from three navigations ago. Confirmed this repeatedly this session (a hydration-mismatch error and a `useEffect is not defined` error both kept reappearing identically after the underlying code was already fixed and `tsc`/lint were clean). **The fix, not a workaround:** open a genuinely new tab (`tabs_create`) for a trustworthy zero-history console read, or check only the tail of `preview_logs` (small `lines` count) right after a fresh action, or just trust a `curl` of the SSR output — never trust an accumulated `read_console_messages` call at face value.
- **PostgREST (Supabase's API layer) caches the schema and does not always notice a new table immediately after you run `CREATE TABLE` in the SQL Editor.** Symptom: a real, successfully-created table still returns `PGRST205 — Could not find the table 'public.X' in the schema cache` from the app. Fix: run `NOTIFY pgrst, 'reload schema';` in the SQL Editor immediately after any DDL change. Hit this for real this session with `google_drive_connections`.
- **A "use client" file must never do a VALUE import (only `import type`) from a file that imports a Node-only package** (here: `googleapis`, transitively `fs`/`child_process`). It bundles the whole module client-side and breaks with a real, confirmed `Module not found` error, not a lint warning. See §3's Drive integration writeup — `lib/driveTemplate.ts` exists specifically to keep this boundary clean going forward.
- **The `computer` tool's `scroll_amount` caps at 10** — passing more errors instead of clamping. Use `javascript_tool`'s `scrollIntoView()`/`scrollTo()` for a specific target instead of relying on `computer scroll` for long pages.
- **Google Cloud OAuth in "Testing" publishing status only works for accounts explicitly added as test users**, and shows an "unverified app" warning every time regardless — expected, not a misconfiguration; click through "Advanced → Go to [app] (unsafe)" as the developer's own test account.
- **Indian Kanoon's own search ranking favors whichever document repeats the query terms most** — for a heavily-cited landmark case that's often a *later* citing case, not the original. `WebSearch site:indiankanoon.org <title> <year/citation>`, then confirm the returned doc's date/citation actually matches, is the only reliable pattern found — still true this session.
- **`gh` CLI is not installed by default on this machine.**
